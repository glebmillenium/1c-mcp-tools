# Установка CFE через HTTP/MCP

Расширение публикует три ограниченных инструмента: `extension_inspect`,
`extension_validate`, `extension_install`. Они работают с **готовым CFE**;
сборка EDT/XML выполняется отдельно. Основная конфигурация CF не поддерживается.
Никакой произвольный BSL и команды ОС эти инструменты не принимают.

Требуется платформа **8.3.22 или новее**; сборочная проверка выполнена на
8.3.27.2130. Параметр `РасширенияКонфигурации.Создать(Данные)` позволяет читать
имя и платформенный хеш кандидата без его установки. См.
[описание платформы 1С](https://wonderland.v8.1c.ru/blog/razvitie-rasshireniy-8322/).
Проверка модулей не заменяет интеграционный прогон HTTP на конкретной ИБ.

## Первоначальная настройка на тестовом стенде

Настройку выполняет администратор в обычном интерфейсе 1С, без `execute_code`:

1. Установить актуальный `mcp_tools.cfe` обычным административным способом,
   применить изменения структуры и открыть новый сеанс. Первую установку
   собственного HTTP API нельзя выполнить через еще отсутствующий API.
2. Выдать учетной записи для инспекции роль `mcp_ЧтениеРасширений`. Для установки
   нужна отдельная роль `mcp_УстановкаРасширений` и штатные права платформы на
   администрирование расширений. Роли не повышают привилегии программно.
   Права, необходимые самой конфигурации для входа и HTTP-сервису, настраиваются отдельно.
3. Вызвать `extension_inspect` с именем известного расширения. Сверить базу,
   пользователя и версию; сохранить `stand_fingerprint` именно этого стенда.
4. Администратору назначить `mcp_НастройкаУстановкиРасширений`. В «Функциях для
   технического специалиста» открыть стандартные формы констант:
   - `mcp_СтендУстановкиРасширений`: проверенный `stand_fingerprint`;
   - `mcp_КаталогКопийРасширений`: абсолютный путь существующего постоянного
     каталога на сервере 1С. Учетной записи процесса 1С нужны права записи/чтения;
   - `mcp_УстановкаРасширенийРазрешена`: включить **последней**.
5. Рабочей учетной записи установки не выдавать роль изменения этих настроек.
   Учитывать объединение прав остальных ролей: полные права могут разрешать их изменение.

Серверное резервное копирование требует доступа самого **`mcp_tools`** к файловой
системе. На файловом стенде безопасный режим расширения блокирует этот доступ;
администратор отдельно настраивает доверие к административному MCP-расширению и
подтверждает его опасные действия штатными средствами 1С, затем открывает новый
сеанс. Начальный файловый доступ самого MCP требует отдельного bootstrap;
свойства целевого CFE API меняет только по явно переданным параметрам
`safe_mode` и `dangerous_actions_protection`. Интерактивные диалоги API не подтверждает.
Свойства прикладного CFE начальным bootstrap не меняются. Недоступность
каталога копий, в том числе запрет файлового доступа, теперь даёт
`backup_directory_unavailable` до монопольного режима и записи, без приватного
системного текста ошибки в HTTP-ответе.

По умолчанию булева константа выключена, отпечаток и каталог пусты.
Для отключения достаточно снять `mcp_УстановкаРасширенийРазрешена`.
Отпечаток — SHA256 серверной строки соединения в UTF-8 без BOM; это привязка к
адресу подключения, **не уникальный идентификатор содержимого ИБ**. Подмена базы
по прежнему адресу не обнаруживается этим хешем, поэтому исполнитель также
сверяет конфигурацию, версии и согласованный профиль стенда.

## Контракт

Транспорт прежний: `POST <публикация>/hs/mcp/rpc`, JSON-RPC `tools/call`.
MCP-ответ содержит JSON в `content[0].text`; всегда проверять `isError`.

| Инструмент | Обязательные аргументы |
|---|---|
| `extension_inspect` | `name` |
| `extension_validate` | `name`, `cfe_base64`, `sha256`, `expected_stand` |
| `extension_install` | все аргументы validate + `expected_previous_sha256`, `confirm: true` |

`extension_install` дополнительно принимает **необязательные** boolean-параметры
`safe_mode` и `dangerous_actions_protection`. Они явно задают свойства именно
устанавливаемого расширения: безопасный режим и предупреждения об опасных действиях.
Отсутствующий параметр сохраняет текущее свойство; для нового CFE остаётся штатное
значение платформы. `false` выключает соответствующий флаг по решению оператора;
строки, числа и `null` не допускаются. Пользовательская и глобальная защита не меняются.

`name` — точное внутреннее имя. `sha256` — SHA256 переданных байтов CFE,
64 hex-символа. Максимальный размер CFE — 16 MiB (Base64 до 22 369 624 символов).
`expected_previous_sha256` — хеш фактически выгруженного текущего CFE из inspect;
пустая строка означает **расширение должно отсутствовать**. Это обязательная
защита от установки поверх неожиданно измененного расширения.

`inspect` возвращает:

```json
{
  "name": "MyExtension",
  "stand_fingerprint": "…",
  "platform_version": "8.3.27.2130",
  "configuration_name": "УчебнаяКонфигурация",
  "configuration_version": "1.0",
  "current_user": "DeploymentUser",
  "session_id": "7",
  "exists": true,
  "enabled": true,
  "safe_mode": false,
  "dangerous_actions_protection": false,
  "session_safe_mode": false,
  "session_dangerous_actions_protection": false,
  "stored_sha256": "…",
  "stored_platform_hash": "…",
  "session_platform_hash": "…",
  "applied_in_current_session": false,
  "installation_enabled": true
}
```

- `stored_sha256` считается по `ПолучитьДанные()` сохраненного расширения.
- `stored_platform_hash` — платформенная `ХешСумма` сохраненной версии.
- `session_platform_hash` берется из `ИсточникРасширенийКонфигурации.СеансАктивные`.
- `applied_in_current_session` истинно только при совпадении активной сохраненной
  версии и обоих флагов с реально подключёнными в **этом** серверном сеансе.
- `safe_mode` и `dangerous_actions_protection` читаются из сохранённого расширения,
  `session_*` — из `СеансАктивные`; отсутствие соответствующего расширения даёт `null`.
  Для изменения только флагов при прежнем CFE исполнитель также должен подтвердить
  новый фактический сеанс. Переданные настройки не подставляются вместо чтения состояния.

`validate` добавляет `artifact_sha256`, `artifact_platform_hash`,
`changes_data_structure`, `problems: [{severity, description}]`,
`applicable` и `status: "validated"`. Наличие любых проблем, включая предупреждения,
блокирует автоматическую установку первой версии API.

Успех `install` возвращает данные инспекции и:

```json
{
  "operation_id": "uuid",
  "status": "stored",
  "artifact_sha256": "…",
  "artifact_platform_hash": "…",
  "backup_path": "D:\\Backups\\uuid.cfe",
  "backup_sha256": "…",
  "requires_fresh_session_verification": true
}
```

Платформа может изменить упаковку бинарного файла. Поэтому исходный SHA256 и
SHA256 выгруженного CFE представлены раздельно; связь кандидата и сохраненной
версии проверяется через `artifact_platform_hash == stored_platform_hash`.
Затем в новом сеансе ожидается совпадение с `session_platform_hash`.
Для нового расширения резервной копии нет: оба `backup_*` поля пустые.
Для существующего копия записывается **до установки**, затем читается обратно
и проверяется SHA256. Имя файла генерирует сервер; пути от MCP-клиента не принимаются.

## Ограничения и завершение установки

Первая версия API всегда запрашивает короткий монопольный режим текущего сеанса.
Это сериализует проверку прежнего хеша, резервное копирование и запись, а также
позволяет применять расширения с данными. Даже для расширений только с кодом
занятая ИБ возвращает `exclusive_access_required` **до записи**. Чужие сеансы,
фоновые задания и Конфигуратор API не завершает. После операции снимается только
монопольный режим, установленный самим вызовом.

`status: stored` не означает «применено» и не означает «обработчики обновления выполнены».
Нужно открыть новый серверный сеанс и проверить сохраненный и подключенный хеши.
HTTP keep-alive и новый HTTP-запрос сами по себе не гарантируют новый сеанс 1С;
исполнитель сравнивает `session_id` и фактические хеши. API не обещает
перезапуск публикации или сеанса посредством вымышленного HTTP-заголовка.

Активность и основные роли расширения API не меняет. Безопасный режим и защита от
опасных действий меняются только при явно переданных boolean-параметрах. Если оно
осталось неактивным или не подключилось, проверка применения не пройдет.
Модель сервиса/разделение данных требуют отдельного интеграционного теста:
неоднозначное имя в доступной области отклоняется.

Ошибки содержат `operation_id`, `status`, `error_code`, `message`.
`exclusive_access_required`, `installation_disabled`, `validation_failed`
возвращаются до записи. Ошибка проверок после получения монопольного режима —
`status: rejected`, `error_code: install_rejected`. После начала `Записать()`
исключение дает `status: unknown`, `error_code: write_outcome_unknown`;
резервная копия сохраняется и ее путь включается в ответ, если она была создана.
Если не подтверждено снятие собственного монопольного режима, результат всегда
`status: unknown`, `error_code: exclusive_release_unknown`, даже если запись
ещё не началась. Такой ответ тоже сохраняет карантин стенда у клиента.
Неопределенный результат, обрыв связи и timeout нельзя повторять автоматически.
Сначала выполнить инспекцию, проверить состояние и журнал регистрации.
Автоматический откат отсутствует: он сам может менять структуру и данные.
Для необработанной ошибки поле `failure_stage` содержит только фиксированное
имя этапа проверки; BSL, пути, учётные данные и текст системного исключения в это
поле не включаются.

Это административный канал доставки исполняемого кода. Доступ к нему должен
иметь исполнитель развертывания, а не пользователь бизнес-тестов. Установка
произвольного доверенного CFE по последствиям шире обычного запроса данных.
Для удаленной публикации используется защищенный HTTP-транспорт и отдельная
учетная запись; токены, пароль и Base64 содержимое не записываются в аудит.
Журнал `mcp.extension_install` содержит идентификатор операции, этап, имя и хеш.

## Проверки

```text
python -m unittest discover -s tests -p "test_*.py" -v
python -m unittest discover -s tests/integration -p "test_extension_api_live.py" -v
```

Интеграционные тесты выключены без `MCP_EXTENSION_TEST_URL`; параметры описаны
в `tests/integration/test_extension_api_live.py`. Они проверяют инспекцию,
контракт и безопасные отказы; **допустимый запрос установки не отправляется**.
Отдельный живой прогон установки с резервной копией и проверкой нового сеанса
выполняется только на согласованном стенде оркестрацией развертывания.
