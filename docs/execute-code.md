# Выполнение BSL на тестовом стенде

Задача: [1700535](https://infostart.ru/bpm/task/1700535/). Инструмент `execute_code` добавлен в существующий HTTP-сервис и автоматически обнаруживается через подсистему контейнеров. По умолчанию выполнение выключено. `tools/list` показывает описание инструмента даже при выключенном допуске; список может кешироваться, но допуск проверяется при **каждом** вызове на стороне 1С.

## Допуск и настройка

Нужны одновременно:

- отдельная учётная запись с ролью `mcp_ВыполнениеКода` и минимальными бизнес-правами для сценария;
- константа `mcp_ВыполнениеКодаРазрешено = Истина`;
- совпадение константы `mcp_ОтпечатокТестовойБазы` с SHA-256 серверной строки подключения текущей ИБ.

Роль выполнения даёт только чтение двух констант и использование контейнера. Она не включает бизнес-права, настройку платформы, управление пользователями или запись констант. С учётными записями, имеющими право изменения этих констант из **любой** роли, инструмент работать отказывается (`overprivileged_account`). Отказ происходит также в привилегированном контексте. Использование администратора в качестве MCP-пользователя здесь не предусмотрено.

Администратору настройки назначается отдельная роль `mcp_НастройкаВыполненияКода`. После согласования конкретной изолированной тестовой ИБ он выполняет в **серверном** контексте доверенной консоли:

```bsl
Менеджер = Обработки.mcp_ИнструментВыполнениеКода;
Отпечаток = Менеджер.ОтпечатокТекущейБазы();
Менеджер.НастроитьВыполнениеКода(Истина, Отпечаток);
```

Эти методы не опубликованы как MCP-инструменты. Параметры HTTP-вызова не могут включить возможность или изменить привязку. Отпечаток не раскрывает строку подключения; точное совпадение специально закрывает доступ после переноса копии на другой адрес. Изменение адреса, регистра или формата строки подключения может потребовать повторной настройки администратором. Восстановление другой базы по тому же адресу не обнаруживается отпечатком: при восстановлении копий допуск надо отключать в процедуре восстановления.

Отключение выполняется тем же администратором:

```bsl
Обработки.mcp_ИнструментВыполнениеКода.НастроитьВыполнениеКода(Ложь);
```

Отключение влияет на следующие вызовы; уже начатый код оно не прерывает. Новая константа Булево имеет начальное значение `Ложь`, строка отпечатка — пустая. Миграция сама не включает возможность и не назначает роли.

## Вход и результат

Вызов `tools/call`:

```json
{
  "name": "execute_code",
  "arguments": {
    "code": "Результат = Параметры.Количество * 2;",
    "parameters": {"Количество": 21}
  }
}
```

`code` — непустая строка до 16 384 символов. Необязательный `parameters` — JSON-объект, до 16 384 символов после сериализации сервером. Другие аргументы отклоняются. В BSL доступны `Код`, `Параметры` и переменная `Результат`, изначально `Неопределено`. Присвойте последней JSON-совместимое значение: число, строку, булево, массив или структуру. Не возвращайте объект документа, таблицу значений или ссылку: сформируйте из них структуру с нужными полями.

HTTP-сервис возвращает обычный MCP `CallToolResult`; в `content[0].text` находится JSON:

```json
{"execution_id":"UUID","status":"succeeded","result":42}
```

При отказе или ошибке `isError=true`, например:

```json
{"execution_id":"UUID","status":"failed","error_code":"disabled","message":"Выполнение кода не разрешено серверной политикой. Код не выполнялся."}
```

Основные коды: `role_required`, `overprivileged_account`, `disabled`, `stand_mismatch`, `policy_unavailable`, `transaction_active`, `invalid_code`, `invalid_arguments`, `invalid_parameters`, `execution_failed`, `result_too_large`, `audit_unavailable`.

JSON значения результата ограничен 32 768 символами. При превышении возвращается ошибка, а не обрезанный JSON. Ограничение проверяется после выполнения и сериализации: оно ограничивает ответ, но не потребление памяти BSL. Сообщение ошибки выполнения ограничено 2 048 символами. `isError=true` **не означает**, что до ошибки ничего не изменилось.

Python-прокси передаёт `isError` до MCP-клиента; прежние текстовые и графические результаты инструментов остаются поддержаны. Для полного `CallToolResult` требуется MCP Python SDK `>=1.27,<2` (проверено на 1.27.0). Обновление зависимостей: `python -m pip install -r src/py_server/requirements.txt` в виртуальном окружении проекта.

## Границы исполнения и журнал

Код исполняется в безопасном режиме платформы; для разделителей данных также включается безопасный режим разделения. Повышения привилегий нет. Это **не режим только чтения и не транзакционная песочница**. Разрешённые права могут позволять запись, проведение документов, вызов прикладных методов. Внешние действия обработчиков нельзя отменить откатом БД. Перед допуском стенда его реальные почтовые, ЭДО, платёжные и другие внешние интеграции должны быть изолированы. Безопасный режим нельзя отключать ради прохождения теста; нужные привилегированные действия оформляются отдельным проверенным инструментом.

Автоматической транзакции вокруг кода нет. Если код оставил открытую транзакцию, она отменяется и возвращается ошибка. Ранее зафиксированные изменения и внешние действия могли сохраниться. Выполнение внутри уже активной транзакции запрещено.

События `mcp.execute_code` содержат `execution_id`, статус, длительность и SHA-256 кода; пользователя и сеанс сохраняет журнал регистрации платформы. Изменение допуска отмечается событием `mcp.execute_code.policy`. Исходный код, значения параметров, результат, ошибки и строка подключения в эти события не включаются. Детали исключения доступны вызывающему клиенту, поэтому клиентские трассы также должны храниться с соответствующими правами.

Если запись начала не удалась, BSL не запускается. Если запись завершения не удалась, возвращается `audit_unavailable` с предупреждением, что код уже мог выполниться. Настройки уровня и хранения журнала регистрации остаются ответственностью администратора: успешный вызов записи сам по себе не доказывает, что события не отключены политикой журнала. На приёмке нужно фактически найти события прогона.

Прокси скрывает содержимое запросов, ответов и исключений `execute_code` в своих логах, включая DEBUG. При штатном запуске через `main.py` DEBUG SDK `mcp` выключен, а фильтр обработчиков полностью заменяет текст, аргументы и traceback сообщений `mcp.*` нейтральным сообщением. Это защищает также ошибки разбора протокола: SDK может включить исходный BSL в `ValidationError` на уровне ERROR ещё до вызова инструмента. Уровень, имя SDK-логгера и место события остаются доступны. Фильтр установлен на существующие root-обработчики, собственные обработчики дочерних `mcp.*` и резервный обработчик; он не меняет сообщения собственного прокси и прежнее логирование старых инструментов.

При встраивании `MCPProxy` в другой процесс вызовите `setup_logging()` из `src.py_server.main` **после** настройки обработчиков журналирования. Если затем добавляете или заменяете обработчики, повторите вызов. Одного уровня INFO недостаточно для сокрытия исключений SDK.

У HTTP-клиента прежний таймаут 30 секунд. Он **не останавливает исполняющийся BSL**; произвольный код также не ограничен по времени и памяти. После обрыва или таймаута повторять вызов автоматически нельзя. Нужно сверить пользователя, время и событие `started` в журнале, проверить сеанс и фактический результат. Если клиент не получил `execution_id`, поиск выполняется по пользователю, времени и хешу исходника. Остановка зависшего сеанса выполняется администратором адресно. Для гарантированного ограничения ресурсов нужен отдельный процесс/стенд и механизм управления его жизненным циклом.

## Проверки перед включением

Локальные тесты транспорта и метаданных (без базы и без пользовательских файлов `test_*.py` в корне):

```powershell
venv\Scripts\python.exe -m unittest discover -s tests -v
```

Они проверяют регистрацию XML, отсутствие у исполнителя прав записи политики, сохранение `isError` через фактический обработчик SDK, совместимость результата `execute_query`, отсутствие payload в логах и отсутствие повторного HTTP-вызова при таймауте. Эти тесты не доказывают работоспособность BSL в платформе.

Интеграционный набор выполняется **только явно** на согласованном стенде, без изменения бизнес-данных:

```powershell
# MCP_TEST_URL, MCP_TEST_USERNAME, MCP_TEST_PASSWORD задаются локально, не в Git.
$env:MCP_TEST_EXECUTE_CODE_STATE = 'enabled'
venv\Scripts\python.exe -m unittest discover -s tests/integration -v
```

Для проверки отказов повторите один и тот же набор под подготовленными учётными записями/настройками с ожидаемым состоянием `disabled`, `role_required`, `overprivileged_account` или `stand_mismatch`. Тесты не переключают допуск сами. Отсутствие переменных приводит к пропуску и не считается приёмкой. Набор проверяет вычисление, параметры, безопасный режим, ошибки BSL, длину исходника и результата. Отдельно администратор проверяет события журнала и отказ при изменении привязки без рестарта HTTP-сервиса.

Для сборки используйте отдельную пустую ИБ: `CREATEINFOBASE`, затем `DESIGNER /LoadConfigFromFiles <src/1c_ext> -Extension mcp_tools`, `/CheckConfig -Extension mcp_tools -Server -ExternalConnection -ExtendedModulesCheck`, обязательно `/CheckModules -Extension mcp_tools -Server -ExternalConnection -ExtendedModulesCheck` и `/DumpCfg <build/mcp_tools.cfe> -Extension mcp_tools`. Каждый шаг требует нулевого кода выхода и проверки отдельного `/Out`-журнала. Не используйте эти команды против пользовательской базы для получения сборочного файла. Применимость расширения и реальные права дополнительно проверяются в целевой тестовой конфигурации.
